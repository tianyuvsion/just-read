RAG检索增强生成：模型答不上来的那部分，去外面找

大模型的知识被冻结在训练那一刻，也拿不到你公司的内部文档。RAG 的做法很直接：先把资料切成块存好，提问时按语义捞出最相关的几块，塞进提示词再让模型作答。整页讲的就是这条链路上每一步为什么存在、会在哪里断。

04

嵌入与检索：把"像不像"变成算术

嵌入模型把一段文本压成一个几百到几千维的坐标。语义接近的文本，坐标就接近——检索因此变成一次最近邻查找。

05

召回 + 重排：一个代价换精度的漏斗

没有任何单一检索器同时做到"快而全"和"准"。工程上的答案是串两级，各干各擅长的事。

08

出问题时，先分清是哪一种坏

RAG 的失败集中在两处，症状很像，修法完全不同。分不清就会修错地方。

检索侧

上下文精确率

取回来的块里，有多少条是真的相关。低就是塞了噪音，压低 top-k 或加重排。

检索侧

上下文召回率

该找到的块，有多少进了候选。低说明检索漏了，查分块、加混合检索、放大 top-k。

生成侧

忠实度

答案里的每条陈述，是否都能在给定材料里找到依据。这是防幻觉的核心指标。

指标要分开看，因为它们会此消彼长：把 top-k 拉大会提高召回率，同时把精确率拉低；把提示词写严会提高忠实度，同时可能让模型变得过度保守、该答的也不答了。所以得先有一份自己的评测集——几十条真实问题配上标准答案就够开始了，比调参重要得多。

09

什么时候不该用 RAG

RAG 不是"给模型加知识"的默认答案。这几种情况，别硬上：

换个做法

语料能整个装进上下文

几页文档、一份合同、一个产品手册——直接全文给模型，长上下文模型比检索更省事也更准。检索的价值随语料规模增长，语料小的时候检索只是在引入误差。

换个做法

要的是聚合，不是查找

"上个季度一共多少单"这类问题需要遍历全库统计，向量检索按相似度返回几条，天然答不了。这类需求应该走结构化查询，让模型生成 SQL 去查数据库。

换个做法

知识本身在快速变化

价格、库存、库存量这类每秒都变的数字，不该进索引——索引有同步延迟。这类要实时调接口，检索只负责相对稳定的文档。

先补别的

问题是模型能力不够

如果给足了正确材料它还是推理不出来，那是推理或提示词的问题，再堆检索也没用。先用正确的上下文手工测一轮，能迅速分清这两种情况。

10

一个能跑起来的最小骨架

先跑通这条线，再往里加混合检索、重排、评测。顺序反了会很难判断是哪一步在起作用。

# 1. 索引：切块 → 嵌入 → 存起来（离线，跑一次）
chunks = split(document, size=512, overlap=64)
for c in chunks:
    c.vector = embed(c.text)          # 与查询端必须同一个模型
store.add(c.vector, c.text, c.source) # 原文和出处一起存，便于回溯

# 2. 查询：嵌入 → 检索 → 拼提示词 → 生成（在线，每次请求）
q = embed(question)
hits = store.search(q, top_k=20)        # 先多召回，别在这一步抠
hits = rerank(question, hits)[:5]          # 精排到少量，省 token 也提准

answer = llm(prompt=f"""
    只依据下面的材料回答。材料里没有就说"文档中没有提到"。
    每条结论后面用 [n] 标出它来自哪一段。

    材料：
    {format_with_index(hits)}

    问题：{question}
""")

整页的一句话总结

RAG 的绝大部分质量问题出在检索侧，而不是模型侧。遇到答得不好，第一件事永远是把召回的块原样打印出来看一眼——是没找对，还是给了没用。这个三秒的动作能省掉大量调参。
